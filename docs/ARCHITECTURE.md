# Architecture

ASC Remote Hub is a self-hosted, multi-user **Model Context Protocol** gateway. The central server accepts remote **Streamable HTTP MCP** requests from any compatible client, authenticates each request with OAuth, and relays supported tools to Windows or Linux agents.

## Components

| Component | Role |
| --- | --- |
| **Hub server 1.2.0** | Python HTTP service; MCP JSON-RPC endpoint, OAuth authorization and client registration, account dashboard, device queues, diagnostics. |
| **SQLite** | Users, hashed device credentials and OAuth tokens, permissions metadata, aggregated tool usage, errors and performance measurements. WAL is enabled. |
| **Agent 1.1.0** | A Python process on Windows or Linux; initiates outbound HTTPS requests, announces tool capabilities and executes approved operations locally. |
| **Installer 1.1.0** | An npm-compatible CLI archive generated by the Hub for the configured public hostname; validates the agent package and configures startup. |

```text
  ChatGPT        Cursor      OpenMausBot        Other MCP clients
      \            |             |                    /
       \___________|_____________|___________________/
                           |
               Streamable HTTP + OAuth
                           |
                    +------------+
                    | ASC Remote |
                    |    Hub     |
                    +------------+
                     ^          ^
         outbound HTTPS        outbound HTTPS
                     |          |
              Windows agent   Linux agent
```

Agents initiate connections to the server. No inbound desktop or SSH ports are required on agent machines. The Hub's public origin is controlled by `ASC_HUB_URL`.

## MCP and OAuth

1. A client discovers OAuth metadata and registers a public client with dynamic client registration (DCR).
2. The Hub validates HTTPS web callback URLs or loopback HTTP callbacks with explicit ports for native applications.
3. A user confirms access on the Hub's consent page. Authorization code + **PKCE S256** binds the code to that client and the exact redirect URI.
4. OAuth bearer tokens are bound to the Hub's MCP resource and a single user. The client invokes MCP `initialize`, `tools/list` and `tools/call` over HTTPS.
5. Each forwarded tool call checks that the specified device belongs to the token's user.
6. A user can list and revoke application-specific tokens without affecting other OAuth clients.

OAuth client ID metadata documents (CIMD) are not advertised; clients must support DCR. Existing authenticated ChatGPT connections are compatible with the vendor-neutral OAuth flow.

## Agent execution and scheduling

Agents run with their Windows/Linux account privileges and enforce configured capabilities. A worker pool provides up to **four** concurrent job slots: independent read-only tools can execute while long-running operations are pending, while potentially mutating command/file operations and GUI-input operations use separate serial execution lanes. Server-side queues and pending jobs are in memory.

A heartbeat runs while long commands are executing, allowing the Hub to distinguish busy agents from disconnected devices. Agent result retries do not re-execute a completed side-effecting tool. Command timeouts and agent restarts still require application-level care.

## Security boundaries

```text
OAuth token → account identity → device owner check → device credential
                                             |
                          local agent permissions and file roots
```

The allowed file roots protect built-in file tools, **not** arbitrary programs executed when command permissions are enabled. Windows GUI operations require an active interactive session. The Hub operator and OS administrators are trusted: traffic is **not end-to-end encrypted from the Hub**.

Optional full traces (`ASC_HUB_TRACE_PAYLOADS=1`) apply to **all** authenticated accounts, are separated by user/device in private storage and can contain sensitive commands, documents or screenshots. Their lifecycle must be managed by the Hub operator.

## Known limits

- One server process; queues are not durable across Hub restarts.
- Background process handles may not be recoverable after agent restarts.
- Long-running or unsafe operations can wait behind other tasks in their execution lane.
- Screen capture and window control depend on a live Windows desktop.
- File operations and returned content are deliberately size-bounded.
- Designed for personal or small-group administration, not distributed HPC scheduling.
